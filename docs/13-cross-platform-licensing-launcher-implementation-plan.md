# Desktop2Stereo 跨平台授权客户端与启动器实施计划

## 0. 当前执行指令（2026-09-10）

### 0.1 项目范围

- 客户端仓库：`desktop2stereo-vulkan/`
- 服务端仓库：`desktop2stereo-site/`
- 本计划文件：`desktop2stereo-vulkan/docs/13-cross-platform-licensing-launcher-implementation-plan.md`

### 0.2 当前实现目标

按照本计划继续完成客户端以下核心流程：

2. 设备绑定。
3. 授权获取与校验。
4. 登录态和授权状态持久化。
5. 网络异常、凭证失效、绑定失败和授权失效等错误处理。
6. Launcher 界面中的状态展示和用户操作闭环。

## 1. 文档范围

本文只负责 `desktop2stereo-vulkan` 客户端：Windows、Linux、macOS 启动器，设备身份，
安全存储，授权选择，离线凭证验证，在线租约，Runtime 二次门禁，以及三平台打包发布。

服务器端账号、授权状态机、订单、支付、余额、邀请、提现、管理后台和部署由
`desktop2stereo-site/docs/01-cross-platform-licensing-server-implementation-plan.md` 负责；
服务器部署以 `desktop2stereo-site/docs/d2s.site.md` 为唯一基准。本文不再维护服务器表结构、
支付实现或腾讯云/Cloudflare 部署步骤。

截至 2026-09-04，Windows 启动器已有基础实现，但仍需迁移到 `desktop2stereo-site` 的
`/api/v1` 契约并重新验收；Linux x86_64、macOS arm64 正式启动器、生产公钥和三平台发布
流水线尚未完成。全部验收门通过前，不得把客户端标记为生产可用。

## 2. 客户端目标与边界

- Windows x86_64、Linux x86_64、macOS arm64 提供一致的登录、授权选择和启动体验。
- 支持设备码登录、一个账号多份授权、在线、7/14/30 天离线和永久绑定模式。
- 离线时只信任服务端 ES256 签名凭证和本地可信时间，不信任本地可编辑配置。
- 在线模式持有短期租约并定期续期；租约到期后安全停止受保护 Runtime。
- 启动器和 Runtime 各执行一次授权检查，不能通过直接运行 Python/EXE 绕过。
- 凭证失效时明确阻止受保护功能并给出可操作错误，不使用毒化模型或错误画面。
- 客户端不计算可信价格、不确认支付成功、不修改授权状态、不包含服务端私钥或支付 Secret。

## 3. 组件边界

### 3.1 共享授权核心

在 `src/desktop2stereo/auth/` 维护无 UI 的共享模块：

- API 客户端与稳定错误码映射。
- 设备指纹标准化与摘要。
- Device Authorization Grant 轮询状态机。
- Access Token 内存管理、Refresh Token 安全存储和刷新。
- 公钥清单、ES256 JWS 验证、授权选择与本地可信时间。
- 在线租约申请、续期、退出和到期通知。
- Runtime 门禁结果与诊断事件。

共享核心不能直接依赖 Flet 页面，也不能在日志中输出访问令牌、刷新令牌、完整凭证、设备
原始标识或个人支付资料。

### 3.2 启动器

启动器负责登录 UI、授权列表、设备/模式操作、购买入口、安全存储、单实例锁、Runtime
子进程启动和退出清理。登录后必须先完成当前设备绑定；模式操作由服务端按授权 ID、设备
指纹和状态机执行。在线模式显示在线心跳说明；离线模式必须选择 7/14/30 天并在服务端
签发、客户端验签后缓存离线凭证；永久模式必须显式输入 `PERMANENT` 二次确认，确认后
不可降级。切回在线模式时清除本地离线凭证，避免旧凭证绕过新的在线模式。启动器只管理
自己创建的进程，不搜索或结束系统中的其它 Python 进程。

### 3.3 Runtime 二次门禁

`app_runtime.bootstrap` 和实际受保护运行入口必须重新读取授权上下文并验证：产品、授权 ID、
设备摘要、模式、签名、有效期和在线租约。只设置环境变量、命令行参数、标志文件或篡改
`settings.yaml` 不能绕过门禁。

## 4. 服务器 API 对接

权威契约为 `desktop2stereo-site/docs/desktop2stereo-api.md`，基础地址生产使用
`https://100393.com/api/v1`；本地服务端对应 `http://127.0.0.1:3000/api/v1`，部署或测试环境可通过
`D2S_API_BASE_URL` 覆盖，客户端不得在业务
代码中散落服务地址。客户端至少对接：

- `POST /device/authorize`、`/device/token`、`/device/cancel`。
- `GET /license/list`、`/license/status`、`/license/keys`。
- `POST /license/activate`、`/switch`、`/change-mode`、`/renew`。
- `POST /license/offline/issue`、`/offline/extend`。
- `POST /license/revoke/free`、`/revoke/paid`。
- `POST /license/online/heartbeat`、`/online/logout`。
- `POST /license/permanent/confirm`、`/license/manual-unbind`。
- 需要打开网页时使用 `100393.com` 的订单、邀请、余额和提现页面，不在客户端复制收银台。

D2S 授权接口响应按 `version`、`success`、`request_id` 和稳定 `error.code` 解析，业务字段只从
`data` 解包；未知版本或未知关键字段必须安全失败，并显示 `request_id` 供客服排查。客户端
`AuthClient._d2s_data()` 是唯一的 D2S 成功响应解包入口，设备码兑换也必须经过同一版本校验。
`request_id` 若存在必须是非空字符串，不能通过 `str()` 转换畸形值；D2S 设备码会话中的授权列表
若存在也必须是数组，且每项包含非空字符串 `id`，不能将畸形列表静默当作空授权。账号兼容登录
保留服务端原生授权字段形状，但列表本身仍必须是数组。
错误响应中的错误码、消息和 `request_id` 也不得通过类型转换伪造；错误码异常时按 HTTP 状态映射
为安全错误，诊断 ID 异常时丢弃该 ID。
GUI 的离线周期下拉框只接受精确字符串 `"7"`、`"14"`、`"30"`，不通过 `int()` 接受数字、
浮点数字符串、带空白值或其他服务端不支持的周期。
账号密码登录、刷新、登出和修改密码属于服务端声明的 new-api 兼容入口，继续按其原生响应
格式解析，不得把两种外层格式混用；修改密码使用 `PUT /api/user/self` 的
`original_password`/`password` 字段，并接收密码变更后返回的新 Access Token。网络超时、401、403、409、429 和 5xx 必须分别处理，
不能都显示“网络错误”。本地 loopback 服务地址会显式绕过系统代理，公网服务地址仍保留
系统代理能力，避免本地开发环境的代理变量把 `127.0.0.1:3000` 错误转发为 502。
登录前读取 `/api/user/login/encryption-key`；当服务端返回 `enabled=true` 时，客户端使用
RSA-OAEP-SHA256 加密 UTF-8 密码并提交 `password_encrypted`/`encryption_key_id`，否则使用
服务端兼容的 `password` 字段。加密公钥无效或客户端缺少加密能力时必须安全失败，不能回退发送明文密码。
点击验证码挑战的 ID、图片和尺寸字段必须经过严格类型与非空校验；畸形挑战在进入登录 UI 前
安全拒绝，不得通过字符串或整数强制转换制造可用验证码状态。

## 5. 设备身份

设备指纹采用 `Optimal` 策略：多源采集、规范化、固定顺序拼接后使用 SHA-256 合成。授权绑定
不能依赖单一硬件标识，也不采集 MAC 地址、IP 地址等低稳定性网络信号。当前
`fingerprint_version=2` 的采集源如下：

| 平台 | 高稳定性信号 | 中等稳定性信号 |
| --- | --- | --- |
| Windows | SMBIOS UUID、CPU 型号 | Machine GUID |
| Linux | 主板产品 UUID、CPU 型号 | `/etc/machine-id` 或 `/var/lib/dbus/machine-id`、根文件系统 UUID |
| macOS | IOPlatformUUID、CPU 型号 | 根卷 UUID |

采集时必须过滤空值、未知值及明显的占位值，例如全零、全八、全 `f`、`000...0a`、
`00:00:00:00:00:0a`、`88888888888888` 等。字符串使用 UTF-8、Unicode NFKC、去除首尾空白、
折叠内部空白并统一小写；特征按固定字段顺序以带字段名的形式拼接，防止采集顺序变化或字段
边界造成碰撞。至少需要两个有效非网络信号；不足时必须显示诊断并阻止绑定，不得随机生成、
使用主机名或使用单一信号冒充稳定指纹。

上传内容仅为 64 字符小写十六进制摘要和正整数 `fingerprint_version`；只有
`/device/authorize` 额外提交规范化平台名称用于设备码诊断。原始硬件标识只在进程内短暂使用，
不得上传、写日志或写入普通配置。`/device/authorize`、`/license/activate` 和
`/license/switch` 必须同时提交 `device_hash` 与 `fingerprint_version`；服务端按版本解释摘要，
不能将不同版本静默视为同一算法。

容器和虚拟机环境可能存在克隆或硬件信号缺失，不能通过随机值绕过；服务端应在后续版本提供
加密绑定或浮动许可证策略。指纹算法升级必须支持版本并存和受控迁移，不能让旧版本客户端
静默占用新设备授权。

## 6. 登录与令牌存储

设备码流程：

1. 启动器请求设备码，显示 `user_code`、验证网址和二维码。
2. 打开系统浏览器，用户在网页完成登录、邮箱验证和批准。
3. 启动器按服务端 `interval` 轮询；处理 pending、slow_down、expired、denied 和成功。
   收到 `slow_down` 时每次增加 5 秒，最大不超过 1 小时，避免服务端限流时继续高频轮询。
4. 成功后 Access Token 仅留内存，Refresh Token 写入平台安全存储。
5. 退出时仅使用匹配服务端结构的令牌调用授权在线退出和账号退出，清除安全存储、内存令牌与本地会话缓存。

账号密码兼容入口使用 `username` 字段（用户界面可继续提示邮箱或用户名），登录与刷新响应
从原生 `data` 字段读取；登录所需点击验证码字段由 `AuthClient.login()` 支持透传。桌面端
刷新和登出不依赖浏览器 Cookie，使用平台安全存储中的 `refresh_token` 请求体完成令牌轮换或会话撤销。
账号启用双因素验证而客户端未提供原生二次验证界面时，必须明确提示用户改用浏览器设备码
授权，不得把 `require_2fa` 响应误报为普通网络或无效响应。

平台安全存储：

- Windows：Credential Manager 或 DPAPI。
- macOS：Keychain。
- Linux：Secret Service/libsecret；服务不可用时只提供本次会话登录，不将 Refresh Token
  降级保存到明文文件。
- `TokenStore` 在存储层强制移除 `access_token`，即使调用方误传也不会持久化；Refresh Token
  仍只能进入平台安全存储，安全后端不可用或会话不可序列化时保存失败。

日志、崩溃转储和遥测必须对 Authorization、Cookie、JWS 和设备摘要做脱敏。

## 7. 离线凭证验证

发布包内置“当前键 + 上一键”公钥清单，按 `key_id` 选择 P-256 公钥验证 ES256 紧凑 JWS。
必须验证：

- 算法固定为 ES256，拒绝 `none`、算法替换和未知键。
- `version`、`product=desktop2stereo`、`license_id`、`device_hash` 和模式匹配。
- `not_before <= trusted_now < expires_at`，并对边界条件做自动化测试。
- 试用、离线天数和 features 只能来自已验证 claims。

客户端记录最近服务端签名时间和最高可信本地时间；离线校验使用不回退的 `TrustedClock.now()`，
并在跨进程恢复时检查已记录的本地时间检查点。
时钟明显回拨时进入 `clock_suspect`，只允许
联网校时和重新授权；不能通过删除普通缓存恢复离线运行。凭证缓存应使用平台安全存储或受
完整性保护的本地数据，删除缓存只会要求重新联网，不会产生新权限。在线签发或续期返回的 JWS
必须先由共享核心验签，再原子替换本地缓存；签发和续期都必须经过该流程。`offline` 模式只接受 7/14/30 天，`permanent`
模式使用服务端签发的永久有效期和 `offline_period_days=0`，不能由客户端自行延长 claims。
离线回退还必须存在有效的持久化可信时间检查点；检查点缺失或损坏时必须回到联网验证，不能
回退到本机当前时间继续离线启动。

## 8. 在线租约与运行期行为

- 仅 `online` 模式在 Runtime 启动前申请在线租约。必须区分两个时间参数：`TTL` 是断网后
  在线租约仍可使用的宽限时间，心跳是在线客户端续租的检测/刷新周期；在线用户在心跳持续
  成功时不会因为 TTL 到期掉线，TTL 也不等同于离线授权的 7/14/30 天有效期。当前服务端
  实际配置为 TTL 2 小时、默认心跳 15 分钟；TTL 不得低于 1 小时，生产环境推荐 2～4 小时，
  在线检测心跳推荐 15～30 分钟。
- 在线检测时间基线必须集中遵循以下参数；调整时同步服务端配置、客户端边界、监控告警和验收用例：

  | 参数 | 当前值 | 推荐值/边界 | 说明 |
  | --- | --- | --- | --- |
  | 在线租约 TTL（断网宽限） | 2 小时 | 推荐 2～4 小时，最低 1 小时 | 不决定持续在线用户的请求频率；过短会降低断网容错 |
  | 在线心跳间隔 | 15 分钟 | 推荐 15～30 分钟；服务端不得低于 5 分钟 | 在线用户通过心跳续租，避免仅依赖 TTL 到期刷新 |
  | 活跃会话/续租 TTL（如服务端单独配置） | 当前未拆分 | 心跳间隔的 2～3 倍 | 例如心跳 15 分钟时取 45 分钟；不得与在线租约 TTL 混淆 |
  | Access Token 有效期 | 以服务端实际响应为准 | 推荐 5～15 分钟 | 业务请求优先本地验签，不因短 Token 频繁查库 |
  | 心跳随机抖动 | ±10% | 固定保留 | 避免大量客户端同时刷新形成尖峰 |
- 客户端以服务端返回的 `heartbeat_interval` 为准，缺失时使用 15 分钟默认值，并对每次心跳加入
  ±10% 的随机抖动，避免大量客户端同时刷新造成请求尖峰。为保护 6 Mbps 带宽，客户端将异常
  或过于激进的服务端间隔限制在 5 分钟至 1 小时；服务端部署不应低于 5 分钟，正常推荐保持
  在 15～30 分钟。TTL 取值变小不会直接增加持续在线用户的请求量，主要影响请求量的是心跳
  和刷新频率；因此不能通过缩短 TTL 代替在线会话检测或账号共享风险控制。
- 心跳响应返回 `server_time`；客户端在当前进程内使用服务端时间锚点和单调时钟计算租约剩余时间，
  不因本机墙上时钟快调或回拨而误判租约。旧服务端缺少该字段时才使用本机时间兼容回退。
- 每次在线租约响应都必须返回非空字符串 `lease_token`、有效的 `expires_at` 和必要的时间参数；
  缺失或类型异常时必须安全失败，不能把畸形值转换成字符串或沿用旧租约令牌掩盖服务端契约错误。
- 按 1 万在线用户、单次心跳请求和响应合计约 2 KB、6 Mbps 出口带宽估算，验证请求平均压力如下：

  | 心跳间隔 | 平均 QPS | 验证流量 | 占 6 Mbps 理论带宽 |
  | --- | ---: | ---: | ---: |
  | 30 分钟 | 5.6 | 11 KB/s | 约 1.5% |
  | 15 分钟 | 11.1 | 22 KB/s | 约 2.9% |
  | 5 分钟 | 33.3 | 67 KB/s | 约 8.9% |
  | 1 分钟 | 166.7 | 333 KB/s | 约 44.4% |

  以上占比按 `6 Mbps ≈ 750 KB/s` 复核，未计入 TLS、重传和业务流量；若按 80% 可用带宽估算，
  占比还会进一步升高。因此 15～30 分钟是默认建议，5 分钟只是安全下限，1 分钟不应作为生产
  配置。服务器 CPU、内存和 Redis/JWT 校验通常不是 1 万在线规模下的主要瓶颈，6 Mbps 带宽
  及其与业务流量的竞争才是主要约束。心跳响应在保留 `lease_token`、`expires_at`、`server_time`
  和 `heartbeat_interval` 等必要字段的前提下应保持极小，业务请求合并续租作为后续优化，但
  不得改变租约失效语义。
- 若完全依赖 TTL 到期刷新，1 万在线用户的平均刷新压力约为：TTL 4 小时 0.69 QPS、2 小时
  1.39 QPS、1 小时 2.78 QPS、30 分钟 5.56 QPS、15 分钟 11.1 QPS。该流量通常可由服务端
  承受，但短 TTL 会降低断网容错并放大集中刷新风险，因此 TTL 最小值固定为 1 小时，并对
  客户端刷新和心跳统一加入 ±10% 抖动。
- 服务端应通过 `server_time`、`expires_at` 和 `heartbeat_interval` 下发实际时间参数；客户端
  必须记录实际采用的参数，便于排查租约误失效和请求尖峰。若业务流量已占满 6 Mbps，必须优先
  保证业务流量，并通过监控调整心跳、限流和刷新策略；不能单纯缩短 TTL 来加强账号共享检测。
- 同一授权被占用时显示占用状态和处理建议，不自动踢掉另一运行实例。
- 临时断网可运行到已签发租约截止；截止前持续重试并采用有上限的退避，租约到期后停止受保护 Runtime。
- 客户端调度下一次心跳时不得越过当前 `expires_at`；若剩余时间不足以安全发起下一次心跳，
  必须直接标记租约失效并停止受保护 Runtime，不额外发送已过期租约请求。
- 到期后停止新帧提交、保存可安全保存的本地设置并退出受保护 Runtime。
- 正常退出调用 `/license/online/logout`；异常退出依靠短租约自然回收。
- 系统睡眠/唤醒、网络切换和本地时钟变化后立即重新确认租约。

在线租约令牌只驻留当前运行会话，不写入 `settings.yaml` 或长期安全存储。

- 单元：设备摘要、错误映射、JWS、时间边界、租约退避、授权选择和状态转换。
- 集成：设备码单次消费、令牌刷新/重放、离线签发、在线冲突、撤销和退出清理。
- 安全：篡改 JWS、替换公钥、未知算法、发布包 Secret 扫描、畸形授权列表、缺失可信时间检查点、
  直接 Runtime 入口和参数注入；恶意软件扫描在隔离 Ubuntu 作业中使用 ClamAV 执行并留存 CI 结果。
- 打包：正式产物不包含开发入口、私钥、测试令牌、`.env` 或用户本地设置。
- 启动器回归：三平台 native 与脚本入口只回收自身子进程；ready 握手成功后移交 Runtime。
- 实机：Windows 11 x86_64、Linux x86_64、macOS arm64 的安装、首次运行、升级和卸载。

测试证据、当前实现路径和状态同步维护在 `docs/requirements-matrix.md`。
